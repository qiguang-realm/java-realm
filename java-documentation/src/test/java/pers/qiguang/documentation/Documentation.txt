    DTO主要用于服务层与Controller层之间的数据传输。当后端方法需要接收复杂参数时，通过一个DTO对象来封装多个请求参数，能够提高代码的可读性和维护性。例如，在一个电子商务网站中，当用户提交订单时，Controller层会接收一个包含用户输入信息的UserDTO对象，并将其传递给Service层进行处理。

VO主要用于展示层与后端服务之间的数据交互。它封装了前端页面所需的所有数据，以满足视图层的展示需求。例如，前端页面需要显示用户信息和订单信息，这些数据会被封装在一个UserVO对象中，并传输到前端进行展示。

总的来说，在选择使用VO还是DTO时，应考虑具体的业务需求和系统架构。如果主要是处理前端传入的数据并直接用于视图展示，VO更为合适；若涉及复杂的业务逻辑和跨层数据传输，则宜使用DTO。

public class Product {
    // 数据库映射字段（以分为单位）
    private Long priceInCents;

    // 业务方法：获取元为单位的金额
    public BigDecimal getPriceInYuan() {
        return priceInCents != null
            ? new BigDecimal(priceInCents).divide(new BigDecimal(100))
            : null;
    }

    // 业务方法：设置元为单位的金额
    public void setPriceInYuan(BigDecimal priceInYuan) {
        this.priceInCents = priceInYuan != null
            ? priceInYuan.multiply(new BigDecimal(100)).longValue()
            : null;
    }

    // Getter/Setter
    public Long getPriceInCents() {
        return priceInCents;
    }

    public void setPriceInCents(Long priceInCents) {
        this.priceInCents = priceInCents;
    }
}

@ApiModelProperty(value = "券面值(单位:分，整数类型)", example = "1000")

 * 获取面值对应的元单位金额（用于精确计算）
 * @return 元单位的金额字符串（保留2位小数，如"10.00"），null表示未设置
 * @apiNote 适用于需要精确金额计算的场景，返回值不带单位
 */
public String getFaceValueYuan() {
    return faceValue == null ? null :
            new BigDecimal(faceValue)
                    .divide(new BigDecimal(100), 2, RoundingMode.DOWN)
                    .toString();
}

/**
 * 设置面值（通过元单位字符串）
 * @param yuan 元单位的金额字符串（如"10.00"），null表示清空面值
 * @throws NumberFormatException 当输入不是有效数字格式时抛出
 * @apiNote 输入值将自动转换为分单位存储
 */
public void setFaceValueYuan(String yuan) {
    this.faceValue = yuan == null ? null :
            new BigDecimal(yuan).multiply(new BigDecimal(100)).longValue();
}

/**
 * 获取带单位的格式化面值展示文本（用于界面显示）
 * @return 格式化后的展示文本，包含单位和适当精度：
 *         - 折扣券(02): "8.50折"（强制2位小数）
 *         - 免息按天(04): "30天"（整数）
 *         - 免息按期(05): "3期"（整数）
 *         - 其他类型: "50.00元"（强制2位小数）
 *         null表示未设置面值
 */
public String getDisplayFaceValue() {
    if (faceValue == null) {
        return null;
    }

    BigDecimal yuanValue = new BigDecimal(faceValue)
            .divide(new BigDecimal(100), 2, RoundingMode.DOWN);

    switch (typeCode) {
        case "02":
            return String.format("%.2f折", yuanValue);
        case "04":
            return yuanValue.setScale(0, RoundingMode.DOWN) + "天";
        case "05":
            return yuanValue.setScale(0, RoundingMode.DOWN) + "期";
        default:
            return String.format("%.2f元", yuanValue);
    }
}

设计一个一体化用户认证与授权系统，支持多角色、多端、多平台、多登录方式，实现用户信息的统一集中管理。

该设计方案已在多个电商和社交平台验证，能够满足复杂的业务场景需求，同时保持了良好的扩展性和维护性。

 主要表结构设计如下：
 1. 用户基础表（user）：存储用户的基本信息，不包含认证信息。
 2. 用户认证表（user_auth）：存储多种登录方式的认证信息，如密码、第三方登录的唯一标识等。
 3. 角色表（role）：存储角色信息，如管理员、普通用户等。
 4. 用户角色关联表（user_role）：用户和角色的多对多关系。
 5. 终端信息表（client）：记录用户登录的终端信息，比如Web、Android、iOS等，用于多端管理。
 6. 用户登录会话表（user_session）：用于记录用户的登录会话，支持多端同时登录。

 ### 认证流程
 1. 对于微信登录：客户端从微信获取code，传给后端，后端用code换取openid，然后检查openid是否已存在用户。如果存在，则登录成功，颁发token；如果不存在，可能需要注册或提示绑定手机号。
 2. 对于手机号验证码登录：客户端提供手机号和验证码，后端验证验证码正确后，检查手机号是否已注册。如果已注册，登录成功；如果未注册，可能自动注册或提示注册。
 3. 对于账号密码登录：客户端提供用户名（可能是手机号或用户名）和密码，后端验证密码是否正确。

“多端” 和 “多平台” 不是同一个概念。端是硬件维度，平台是软件/生态维度。

角色（Role）是动态的、可分配的、多对的，关乎“能做什么”；而类型（Type）是静态的、内在的、单一的，关乎“是什么”。

Type解决“你是谁”（身份、数据归属），Role解决“你能做什么”（权限）。

核心区别：维度与目的不同
特性	类型 (Type)	角色 (Role)
核心问题	用户是什么？	用户能做什么？
业务含义	用户的本质身份和数据归属	用户的权限集合和功能范围
可变性	基本不可变（或很少变更）。一个用户注册时是司机，他本质上就是司机，不会变成货主。	动态可变。可以随时给用户分配、收回“VIP用户”、“审核员”等角色。
数量	通常只有一个。一个用户不可能同时是司机端用户和后台用户（尽管账号可以通用，但一次登录只以一种身份操作）。	可以有多个。一个用户可以同时拥有“项目经理”和“数据查看员”两个角色。
设计层面	数据模型层面的基础分类。用于数据隔离和路由。	权限模型层面的动态授权。用于功能控制。
与技术栈关系	与客户端类型（App, H5, 小程序, PC） 强绑定。	与后台功能菜单和接口强绑定。

3. Google (及硅谷风格)
Google等国外大厂在命名上可能更简洁，但思想一致。他们可能不会在所有地方都强制加上DTO后缀，但会通过命名明确表示其职责。

创建请求：CreateXxxRequest

更新请求：UpdateXxxRequest

响应：XxxResponse 或 Xxx

查询参数：ListXxxRequest (包含分页、过滤等)

特点：喜欢使用 Request 和 Response 来明确表示这是网络传输的请求体和响应体，本质上也是DTO。这种风格在国内也很常见，特别是与Web层紧耦合的对象。



场景	推荐命名	示例	说明
创建资源	XxxCreateDTO	UserCreateDTO	强烈推荐这种“实体名+操作+DTO”的形式，主体先行，结构清晰。
更新资源	XxxUpdateDTO	UserUpdateDTO	同上。明确表示这是更新操作的载荷。
查询参数	XxxQueryDTO	UserQueryDTO	专用于复杂查询条件，包含分页、排序、过滤字段等。
简单响应	XxxDTO	UserDTO	返回单个实体的核心信息。
复杂响应	XxxDetailDTO 或 XxxResponse	UserDetailDTO, UserResponse	返回实体的详细信息，或聚合了多个来源的数据。
列表响应	XxxListDTO 或 PageDTO<XxxDTO>	PageDTO<UserDTO>	列表数据通常会用分页包装器包裹单个实体的DTO。

对于线上已有数据的表，添加新字段时确实需要谨慎处理默认值。
对于线上环境，确实应该先添加允许NULL的字段，然后分批更新数据，最后再考虑设置为NOT NULL。

-- 1. 先添加字段（允许NULL）
ALTER TABLE order_info ADD COLUMN exception_status INT COMMENT '异常状态';

-- 2. 在低峰期分批更新现有数据
-- 第一次更新：1-10000条
UPDATE order_info SET exception_status = 0 WHERE id BETWEEN 1 AND 10000;

-- 第二次更新：10001-20000条
UPDATE order_info SET exception_status = 0 WHERE id BETWEEN 10001 AND 20000;

-- 继续直到所有数据更新完成

-- 3. 更新完成后，可以修改字段为非NULL（可选）
ALTER TABLE order_info MODIFY COLUMN exception_status INT NOT NULL DEFAULT 0;
