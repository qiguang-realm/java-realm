    DTO主要用于服务层与Controller层之间的数据传输。当后端方法需要接收复杂参数时，通过一个DTO对象来封装多个请求参数，能够提高代码的可读性和维护性。例如，在一个电子商务网站中，当用户提交订单时，Controller层会接收一个包含用户输入信息的UserDTO对象，并将其传递给Service层进行处理。

VO主要用于展示层与后端服务之间的数据交互。它封装了前端页面所需的所有数据，以满足视图层的展示需求。例如，前端页面需要显示用户信息和订单信息，这些数据会被封装在一个UserVO对象中，并传输到前端进行展示。

总的来说，在选择使用VO还是DTO时，应考虑具体的业务需求和系统架构。如果主要是处理前端传入的数据并直接用于视图展示，VO更为合适；若涉及复杂的业务逻辑和跨层数据传输，则宜使用DTO。

在数据库设计中，金额字段的类型选择非常重要，主要考虑精确度和计算准确性。同时，在Java实体中也需要选择对应的类型，以确保数据在应用程序层能够正确处理。

选择指南
场景	数据库类型	Java类型	说明
通用金额	DECIMAL(12,2)	BigDecimal	标准选择，覆盖大部分场景
高精度价格	DECIMAL(10,4)	BigDecimal	汇率、利率、加密货币
超大金额	DECIMAL(15,2)	BigDecimal	银行、企业级应用
性能敏感	INT/BIGINT	Integer/Long	以分为单位，牺牲可读性换性能
未知金额	DECIMAL(10,2) NULL	BigDecimal	报价、预估等场景
这种设计组合确保了从数据库存储到Java业务逻辑的金额数据始终保持精确和一致。

设计一个一体化用户认证与授权系统，支持多角色、多端、多平台、多登录方式，实现用户信息的统一集中管理。

该设计方案已在多个电商和社交平台验证，能够满足复杂的业务场景需求，同时保持了良好的扩展性和维护性。

 主要表结构设计如下：
 1. 用户基础表（user）：存储用户的基本信息，不包含认证信息。
 2. 用户认证表（user_auth）：存储多种登录方式的认证信息，如密码、第三方登录的唯一标识等。
 3. 角色表（role）：存储角色信息，如管理员、普通用户等。
 4. 用户角色关联表（user_role）：用户和角色的多对多关系。
 5. 终端信息表（client）：记录用户登录的终端信息，比如Web、Android、iOS等，用于多端管理。
 6. 用户登录会话表（user_session）：用于记录用户的登录会话，支持多端同时登录。

 ### 认证流程
 1. 对于微信登录：客户端从微信获取code，传给后端，后端用code换取openid，然后检查openid是否已存在用户。如果存在，则登录成功，颁发token；如果不存在，可能需要注册或提示绑定手机号。
 2. 对于手机号验证码登录：客户端提供手机号和验证码，后端验证验证码正确后，检查手机号是否已注册。如果已注册，登录成功；如果未注册，可能自动注册或提示注册。
 3. 对于账号密码登录：客户端提供用户名（可能是手机号或用户名）和密码，后端验证密码是否正确。

“多端” 和 “多平台” 不是同一个概念。端是硬件维度，平台是软件/生态维度。

角色（Role）是动态的、可分配的、多对的，关乎“能做什么”；而类型（Type）是静态的、内在的、单一的，关乎“是什么”。

Type解决“你是谁”（身份、数据归属），Role解决“你能做什么”（权限）。

核心区别：维度与目的不同
特性	类型 (Type)	角色 (Role)
核心问题	用户是什么？	用户能做什么？
业务含义	用户的本质身份和数据归属	用户的权限集合和功能范围
可变性	基本不可变（或很少变更）。一个用户注册时是司机，他本质上就是司机，不会变成货主。	动态可变。可以随时给用户分配、收回“VIP用户”、“审核员”等角色。
数量	通常只有一个。一个用户不可能同时是司机端用户和后台用户（尽管账号可以通用，但一次登录只以一种身份操作）。	可以有多个。一个用户可以同时拥有“项目经理”和“数据查看员”两个角色。
设计层面	数据模型层面的基础分类。用于数据隔离和路由。	权限模型层面的动态授权。用于功能控制。
与技术栈关系	与客户端类型（App, H5, 小程序, PC） 强绑定。	与后台功能菜单和接口强绑定。

在使用 MyBatis Plus 进行开发时，为了提升查询效率、增强代码可读性与可维护性，合理利用其提供的 Wrapper（条件构造器）来构建查询条件，
是一项非常重要且实用的实践。
Wrapper 作为 MyBatis Plus 的核心特性之一，支持通过链式调用方式灵活组合多种查询条件，从而轻松应对复杂查询场景。
如何通过最佳实践与推荐方式，编写基于 Wrapper 的查询方法，帮助你在实际项目中构建更清晰、高效且易于维护的数据查询逻辑。

1.使用 Lambda 表达式：为了类型安全和避免硬编码字段名，推荐使用 LambdaQueryWrapper 或 LambdaUpdateWrapper。这样在编译期就能检查字段名，并且重构友好。

2.避免硬编码字段名：使用实体类的 getter 方法引用或者 Lambda 表达式来引用字段，而不是字符串。

3.合理使用链式调用：Wrapper 支持链式调用，可以将多个条件连接在一起，使代码简洁。

4.复用 Wrapper：如果多个查询有相同的条件，可以抽象出通用的 Wrapper 方法，避免重复代码。

5.动态条件构建：根据业务逻辑动态添加条件，可以使用 if 语句或者使用 Wrapper 的条件判断方法（如 nonNull 等）。

6.使用 Service 层封装的方法：MyBatis Plus 的 Service 层提供了很多便捷的方法，如 list(Wrapper)、page(Page, Wrapper) 等，可以直接使用。

7.分页查询：进行分页查询时，使用 Page 对象并配合 Wrapper 构建条件。

8.选择正确的 Wrapper 类型：根据操作类型选择查询包装器（QueryWrapper）或更新包装器（UpdateWrapper）。

9.注意条件顺序：条件顺序可能会影响查询性能，比如将过滤性强的条件放在前面。

10.使用索引：确保查询条件能够利用数据库索引，避免全表扫描。

设计金额字段时，需要考虑业务逻辑、数据完整性和使用便利性。以下是对不同情况下的归纳总结：

1.默认值设为0.00的情况：

当业务逻辑上，新记录的金额在未明确指定时，其自然状态为0。例如：新订单的总额、新账户的余额、初始的交易金额等。

为了避免NULL值在计算中带来的问题（如NULL参与运算结果为NULL），同时为了简化代码（不需要频繁检查NULL）。

当字段被定义为NOT NULL时，必须指定默认值（除非在插入时总是显式提供值），而0.00通常是一个合理的默认值。

2.不设置默认值（即允许为NULL）的情况：

当金额字段在业务逻辑上可能处于“未知”或“未确定”状态时。例如：报价单中的价格、预计费用（尚未确定）、实际发生但尚未记录的金额等。

注意：使用NULL需要确保应用程序能正确处理NULL值，并在计算时使用如COALESCE或IS NULL等函数或条件。

3.不设置默认值且不允许为NULL（即必须显式插入）的情况：

当金额字段是必须提供的，且没有合理的默认值。例如：一张发票的金额，在创建发票时就必须已知，不能为0也不能为NULL。

这种情况下，数据库设计会强制在插入时提供该值，否则插入操作会失败。

4.默认值设为其他非0值的情况：

根据业务需求，可能有特殊的默认值。例如：某些服务的最低消费金额、固定费用等。但这种情况相对较少。

总结如下：

情况	设置	说明
1	DECIMAL(10,2) NOT NULL DEFAULT 0.00	最常用的情况，表示金额初始为0，且不能为NULL。
2	DECIMAL(10,2) NULL	允许金额为未知，插入数据时可不提供该字段，默认为NULL。
3	DECIMAL(10,2) NOT NULL	强制要求插入时提供金额，且没有默认值。
4	DECIMAL(10,2) NOT NULL DEFAULT <特定值>	根据业务需求设置特定的默认值。
在实际设计中，我们还需要考虑以下几点：

数据类型：金额字段通常使用DECIMAL或NUMERIC类型，因为它们可以精确表示小数。避免使用浮点数类型（FLOAT、DOUBLE），因为它们有精度问题。

精度和范围：根据业务需要指定精度，例如DECIMAL(10,2)表示整数部分最多8位，小数部分2位。

最后，具体选择哪种方式，一定要与业务需求相结合。

最终建议： 在开始设计前，务必与业务方或产品经理明确每一个金额字段的业务含义和生命周期，这是做出正确技术决策的基础。

最佳实践：手机号码应该用字符串存储，原因：

1.语义正确：手机号是标识符，不是用于计算的数值

2.格式完整：可以保留前导0、国家代码（+86）

3.操作方便：便于验证、格式化显示、提取运营商信息

4.无溢出风险：不受数据类型范围限制

5.国际兼容：支持各种格式的国际电话号码

即使在某些情况下可以用long存储，从数据建模的角度看，字符串才是更合适的类型

选择 VARCHAR(20) 而不是 VARCHAR(11) 的主要原因：

1.国际化兼容：支持各国不同长度的电话号码

2.格式完整：能存储带+号、空格、连字符的格式

3.未来扩展：避免因需求变更而修改表结构

4.成本考虑：VARCHAR(20)比VARCHAR(11)多的存储成本几乎可忽略

5.标准遵循：符合E.164国际标准的最大长度建议

记住：数据库模式修改是昂贵的操作。宁愿开始时就留出合理的余量，也不要因为节省几个字节而将来需要ALTER TABLE。

确实，自动失效对用户体验有影响，但不失效对安全性有重大风险。让我详细分析并给出平衡方案：

🔍 为什么需要Token失效？
安全问题：
1.Token泄露风险：如果Token永久有效，一旦泄露，攻击者可以永久使用

2.设备丢失风险：手机/电脑丢失，攻击者可无限期访问

3.权限变更无法及时生效：用户权限变更后，旧Token仍有效

4.无法强制登出：发生安全事件时无法及时阻断



⚖️ 平衡安全与体验的方案

方案1：滑动过期（Sliding Expiration） - 推荐

方案2：分层过期策略

方案3：智能过期策略


🎯 最佳用户体验实践

1. 无感刷新（Silent Refresh）

2. 智能会话保持

3. 优雅的重新登录引导



📊 推荐的过期策略组合
场景	过期时间	刷新机制	用户感知度
信任设备	30天	自动续期	无感
移动APP	7天	滑动过期	基本无感
日常Web	2-8小时	智能刷新	偶尔提示
公共设备	30分钟	不续期	频繁验证
高危操作	会话级	每次验证	强感知


💡 我的建议
对于大多数应用，采用：
1.默认8小时过期 + 滑动续期（用户活跃时自动续到8小时）

2.记住我选项：勾选后延长至7-30天

3.信任设备：首次验证后可设为长期有效

4.关键操作前：二次验证（密码/短信）


✅ 结论
不要完全不让Token失效，而是：

· 让合理的失效（比如8小时）

· 让智能的续期（用户活跃时自动延长）

· 让用户有选择（记住我、信任设备）

· 让体验更流畅（无感刷新、优雅提示）

这样既保证了安全性，又最大限度提升了用户体验。关键是找到安全与便利的平衡点，而不是二选一。

数据库表之间的关系主要分为以下三种，这也是关系型数据库设计的核心：

1.一对一

定义：表A中的一条记录在表B中有且仅有一条记录与之对应，反之亦然。

应用场景：通常用于字段拆分（如将经常访问的字段和不常访问的大字段分表）、安全隔离（如分离登录信息和个人详情）、继承关系（如单表继承模式）。

实现：任意一方表中设置外键，并为该外键添加唯一约束。

2.一对多（或多对一）

定义：表A中的一条记录在表B中可以对应多条记录，但表B中的一条记录在表A中只能对应一条记录。这是最常见的表关系。

应用场景：主从结构（如一个用户有多篇文章、一个分类有多个商品）。

实现：在“多”的一方（子表）建立外键，指向“一”的一方（主表）的主键。

3.多对多

定义：表A中的一条记录在表B中对应多条记录，反之亦然。

应用场景：复杂的关联关系（如学生与课程、用户与角色）。

实现：单纯的物理表无法直接实现多对多，必须引入一张中间表（关联表）。中间表包含两个字段，分别作为外键指向两张主表，这两个字段通常组成联合主键。

一、「计价单位」：最底层的尺子  pricing_unit
在联合国/世界海关组织标准（UN/CEFACT Recommendation No. 20）中，计价单位有标准的三字母代码（TNE=吨, MTQ=立方米, PCE=件等），直接对应你业务场景中的"按吨""按车""按方""按根"。ISO 21041 也明确了同样的要求。

映射到你的业务：

按吨结算 → Pricing_Unit = 'TON'

按车结算 → Pricing_Unit = 'VEHICLE'

按方结算 → Pricing_Unit = 'CUBIC_METER'

按根结算 → Pricing_Unit = 'PIECE'

package me.zhengjie.enums;

import com.baomidou.mybatisplus.annotation.EnumValue;
import com.fasterxml.jackson.annotation.JsonCreator;
import com.fasterxml.jackson.annotation.JsonValue;
import lombok.Getter;

@Getter
public enum PricingUnitEnum {

    TON(1, "吨"),
    VEHICLE(2, "车"),
    CUBIC_METER(3, "立方米"),
    PIECE(4, "根");

    @EnumValue          // MyBatis-Plus 标记数据库存的值
    @JsonValue          // Jackson 序列化时输出该值
    private final Integer value;
    private final String name;

    PricingUnitEnum(Integer value, String name) {
        this.value = value;
        this.name = name;
    }

    // 反序列化：将数据库的 Integer 转为枚举
    @JsonCreator
    public static PricingUnitEnum fromValue(Integer value) {
        if (value == null) return null;
        for (PricingUnitEnum unit : values()) {
            if (unit.value.equals(value)) {
                return unit;
            }
        }
        throw new IllegalArgumentException("Unknown pricing unit value: " + value);
    }
}


@EnumValue   // MyBatis-Plus 用这个字段的值作为数据库存储值
private final Integer value;

@JsonValue   // Jackson 序列化时也输出这个值
private final Integer value;

MyBatis-Plus 看到 @EnumValue 在 value 字段上，就会调用 getValue() 取 Integer 值写入数据库。


反过来：从数据库读取
当 MyBatis-Plus 查询数据时，读到 pricing_unit = 2，会自动调用 PricingUnitEnum.fromValue(2) 将数字转换成 PricingUnitEnum.VEHICLE 对象，赋给实体类的 pricingUnit 属性。

所以你看到的实体类里仍然是枚举对象，而不是数字。
